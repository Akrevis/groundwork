# /groundwork:docs —— 文档工作流

## 先选模式

调用时跟在命令后面的参数，会以 `ARGUMENTS:` 一行附在本文末尾。看它的第一个词：

| 第一个词 | 模式 | 用 Read 读 |
|---|---|---|
| `init` | 建档：给项目建立文档骨架（每个项目一次） | `${CLAUDE_SKILL_DIR}/init.md` |
| `task` | 待办：把定下来的事写成待办 | `${CLAUDE_SKILL_DIR}/task.md` |
| `wrap` | 收尾：会话结束时把变化写回文档 | `${CLAUDE_SKILL_DIR}/wrap.md` |
| `audit` | 体检：查文档的一致性 | `${CLAUDE_SKILL_DIR}/audit.md` |

**没有参数，或者第一个词不在表里 → 停下问用户要哪个模式，不要猜。** 选定后只读对应的那一份，按里面的步骤做。本文的规则和模板四个模式共用。

## 目录分工

`docs/` 是人和 AI 共享的项目状态，跟着 git 走。**只有 `context.md` 每次会话被强制注入**，其余按需读。**工作区里只放现在成立的东西，发生过的交给 git。**

```
CHANGELOG.md                  仓库根目录：每个版本改了什么
docs/
├── 1-requirements/
│   ├── requirements.md       为什么做、给谁用、长期不做什么
│   └── diagrams/             系统上下文图
├── 2-design/
│   ├── architecture.md       原则与技术约束；当前阶段的架构与已知风险
│   └── diagrams/             结构、行为、数据、部署的图
├── 3-development/
│   └── tasks/                待办：定下来、留给之后的会话去做的
├── 4-testing/
│   └── testing.md            怎么验证：命令、测了什么、测不到什么
├── 5-release/
│   ├── release.md            怎么发布、发布前查什么、怎么回滚
│   └── diagrams/             发布与更新怎么走的图
├── 6-maintenance/
│   └── archive/              做完了、结果还在被依赖的任务背景
├── plans/                    还没定的：这一阶段的草案、未决问题、待验证的事、已知缺陷
├── backlog.md                在这个项目里用 groundwork 时，groundwork 本身带来的摩擦
├── context.md                每次会话注入：是什么、不做什么、模块职责、结构性的坑
├── devlog.md                 ADR：现在有效的决策
└── roadmap.md                阶段表：项目分哪几个阶段走到今天
```

**环节和阶段是两回事。** 环节是软件工程的六段：需求、设计、开发、测试、发布、维护，目录按它编号；阶段是 roadmap 里解决一个问题的一批工作。每个阶段都把六个环节走一遍，所以环节目录里只放现在成立的内容，不按阶段累积。

**一份文档只属于一个环节，就放进那个环节的目录；贯穿全程的，留在 `docs/` 根下。** 话题横跨需求和设计，ADR 记各个环节的决定，roadmap 和 `context.md` 管全局。

**这是通用布局，不是要填满的清单。** 哪个环节没有内容，它的目录就不存在：不写代码的项目没有测试，没上线的项目没有发布。项目可以在环节目录里加自己需要的文件。hook 只认四个路径——`docs/context.md`、`docs/plans/`、`docs/3-development/tasks/`、`docs/6-maintenance/archive/`——其余都是约定（ADR-029）。

| 什么 | 放哪 |
|---|---|
| 成立的决定 | `requirements.md`（为什么做、做到哪）、`architecture.md`（现在是什么样）、`devlog.md`（为什么这样定） |
| 还没定的 | `plans/` |
| 定了还没做的 | `3-development/tasks/` |
| 做完了、结果还在被依赖的任务背景 | `6-maintenance/archive/` |
| 怎么验证、怎么发布 | `testing.md`、`release.md` |
| 每个版本改了什么 | 仓库根目录的 `CHANGELOG.md` |
| 发生过的 | git。例外是 roadmap 的阶段表和 `CHANGELOG.md`：阶段怎么划、哪些改动要告诉使用者、破坏性改动怎么迁移，是判断，git 推不出来 |

**除了 `context.md` 和开局的话题、草案，什么都不预建。** 其余文件和目录第一次真有内容时才出现：空模板是噪音，AI 读到空文件不知道该不该填；空目录 git 不跟踪，换台机器就没了。开局的话题和草案不算空模板——每一份都写着哪一层、哪个阶段还没定，意思清楚（见 `init.md`）。

## 一件事怎么走

```
阶段开始 ─────────────────→ plans/1-<阶段>草案.md
冒出来的问题 ─────────────→ plans/<层级>-<名字>.md
                              │ 定下来，留给之后的会话做
                              v
              3-development/tasks/<序号>-<名字>.md
                              │ 做完
                              v
  结果还会被依赖 → 6-maintenance/archive/ 存一份背景；否则删掉
```

- **当场定、当场做完的事不建文件**，commit 就是记录
- **每个阶段一份草案**：阶段开始时，这一阶段的边界和框架由 AI 起草进 `plans/1-<阶段>草案.md`，起草的规矩在 `decision-order` skill。定下的部分写进 `requirements.md` 或 `architecture.md`、从草案里划掉；要干的活写成待办；全部定完，草案删掉
- **草案默认不拆**，细节就在草案里谈。只有两种情况拆成单独的话题：它会拖得整份草案关不掉——谈了几个会话还没定，别的部分全定了草案也删不掉，注入里一直显示它最靠前；它挪到了后面的阶段——话题里写明「什么时候必须定：第 N 阶段」
- 待办有两个来路：`task` 模式把定下来的事写进去；本次会话开了工、没做完、又没有待办文件的事，由 `wrap` 写进去
- 讨论的先后按 `decision-order` skill 的八层；话题文件名以层级开头，`docs/plans/` 里文件名最小的就是现在该定的

话题有四种结局，四种都离开 `plans/`：

| 结局 | 怎么走 |
|---|---|
| 转成待办 | `task` 模式把它写进 `3-development/tasks/` |
| 定案成设计 | 收尾时先问用户，确认后写进 `requirements.md` 或 `architecture.md` 对应的区 |
| 放弃 | 理由不显然的，问要不要记 ADR；然后删 |
| 顺手做完 | 某次会话里直接解决了；结果是长期成立的事实，就写到它该在的地方（`architecture.md`、`testing.md`、`context.md` 的坑） |

阶段草案的结局是前两种的组合：定下的框架写进 `requirements.md`、`architecture.md`，要干的活写成待办。

只定了一部分不算定：定了的写进对应的文档、从「要解决什么」或草案里划掉，文件留着。

## 命名

| 去处 | 文件名 | 例子 |
|---|---|---|
| `plans/` | `<层级>-<名字>.md`，层级 0～7 | `3-模块划分.md` |
| `plans/` 里的阶段草案 | `1-<阶段>草案.md`，阶段名照 roadmap 阶段表的叫法 | `1-第一版草案.md` |
| `3-development/tasks/` | `<两位序号>-<名字>.md`，按开工顺序 | `01-搭目录骨架.md` |
| `6-maintenance/archive/` | `<完成日期>-<名字>.md` | `2026-10-16-搭目录骨架.md` |

话题的层级按它**影响到的最早一层**算，不看它表面上谈什么。待办插队时，后面的顺延改名（`git mv`）；待办删掉或归档后留下的空号不必补。

## 必备块

每个模板列出必备块，两条规则管所有模板：

1. **块必须在，标题随意**——用项目自己的语言和说法。没有程序解析这些块：hook 只读文件名和 git
2. **空的块写「无」，不省略**——缺一块分不清是忘了还是没有。例外是 `context.md` 和 `CHANGELOG.md`：前者每次会话都被注入，空的一节白占注意力；后者每个版本只写有改动的分类。两者的空节都直接不写

`requirements.md`、`architecture.md`、`testing.md`、`release.md` 的章节带编号（`## 1. …`、`### 1.2 …`）。别的文件引用它们写成「文件名 §编号」（`architecture.md §3.2`），同一份文件里只写 `§3.2`——体检按文件名核对，不写文件名的跨文件引用查不到。

## 模板

### context.md

`context.md` 让 AI 从第一个 token 起就懂这个项目。**每一条都要过三道检查：**

1. **git 推导不出**。技术栈、分支、未提交改动、最近提交、待办列表、过期基线都由 hook 采集——**绝不手写**
2. **AI 不知道自己缺它**。它用到时自己会去查的（架构细节、ADR 全文），给指针不给内容
3. **对任何 clone 这个仓库的人都成立**。只在某台机器上才撞的坑（某个 shell 的转义、本地路径、个人 git 配置）放用户级记忆。判据：换台机器、全新 clone，它还会咬人吗？

**不设行数上限。** 让文件保持小的是三道检查。小仍然重要，但不是为了省 token：长上下文中段的召回率会掉，注入 500 行，关键的 5 行反而被淹没。结构性的坑只收永久、反复撞的；能修的修掉。

```markdown
# <项目> · context

> 最后更新：YYYY-MM-DD
> 每次会话注入。只写 git 推导不出、且 AI 不知道自己缺的事实。

## 是什么
<一句话：给谁用，解决什么>

## 不做什么
- <明确不做的，防止 AI 自己扩范围>

## 顶层模块
| 模块 | 职责（一句话） |
|---|---|

## 结构性的坑
- <任何 clone 这个仓库的人都会撞、每次都撞的>
```

| 块 | 必备 |
|---|---|
| 带日期的头部 | 总是 |
| 是什么 | 总是，最核心 |
| 不做什么 | 强烈建议填，真没有才省略 |
| 顶层模块 | 还没有代码时省略 |
| 结构性的坑 | 没有就省略 |

**日期行重置过期警告。** hook 以最后一次改 `context.md` 的 commit 为基线，之后落下 5 个以上提交就警告，并点名变动的目录。所以收尾改日期并提交，就等于标记「已核对」。不往文件里写 commit hash：写进去的 hash 指向包含它的那个 commit，而 amend、rebase、squash 换掉的正是它。

### 话题（plans/）

```markdown
# <话题>

> 提出：YYYY-MM-DD

## 来源
<实际发生了什么，引出这个话题>

## 要解决什么
- <每个待定的问题、待验证的假设，或要修的缺陷>

## 讨论记录
- YYYY-MM-DD <定了什么；还开着什么>
```

可选一行「什么时候必须定」（比如「开工第 1 步之前」「第二阶段」），给同一层的话题排先后。

**门槛：真的发生过。** 假设出来的问题不记——写下来就是给虚构问题造组件的开始。开局话题的来源是「项目开局，这一层还没定」，过得了这道门槛。

### 阶段草案（plans/）

一个阶段一份。怎么起草——推断怎么找、哪些结论要先搜、出处怎么写——在 `decision-order` skill 里，这里只管文件的样子。开头两块是给用户读的，放在最前面，不被后面的细节淹掉。

```markdown
# <阶段>草案

> 提出：YYYY-MM-DD

## 来源
<这一阶段为什么开始：项目开局，或上一阶段做出了什么；用户说过的想要>

## 要你回答的问题
- <草案里的推断，改写成用户答得上的问题：怎么用、想要什么>

## 全貌
<几行字：这一阶段做到哪，框架大致什么样>

## 草案

### 边界
- 做：<这一阶段做到哪>
- 不做：<砍掉的，逐条，标明挪到第几阶段>

### <第 2～6 层，每层一节>
- 结论：<一个推荐>
- 依据：<用户的原话，或仓库里已经成立的东西>
- 后果：<用户能感觉到的>
- 类别与出处：<属于哪一类；出处，以及它为什么适用。哪类都不属于，写「无，AI 自己的判断」>

## 讨论记录
- YYYY-MM-DD <定了什么、写进了哪；还开着什么；用户坚持、AI 反对的，记下反对的理由>
```

建档或开新阶段时先建、还没起草的那一份，「要你回答的问题」「全貌」写「还没起草」，「草案」写「还没起草」并列出还没定的层。

**门槛：这个阶段真的开始了。** 想到以后可能有的阶段，不预建草案。

### 待办（tasks/）

待办写给之后执行它的会话看，那个会话不需要别的东西就能开工。

```markdown
# <待办名>

> 开立：YYYY-MM-DD

## 目标
<要什么，用自己的话>

## 边界
- 不做：<明确排除的>
- 改哪些文件：<文件和目录>
- 改上面以外的文件，先回来问

## 前提（推断，已确认）
- <用户没说、但这件事建立在上面的每一条，开工前已确认>

## 完成标准
- [ ] <可验证的：一条命令和它的预期结果、一个测得的数字、一个点名的测试>
- [ ] 项目已有的测试全过（没有测试套件就写「无」）

## 现状
<每次覆盖：做完了什么、下一步做什么、卡在哪>

## 自己拿的主意
- YYYY-MM-DD <没问用户、自己定的选择，以及理由>
```

| 块 | 为什么必备 |
|---|---|
| 目标、边界、前提 | 从没人说过的前提往下推，做出来的东西看着完整，方向却是歪的 |
| 完成标准 | 动手前定的是测试；做完再写，只是对做出来的东西的描述 |
| 现状 | 下一个会话靠它接手。覆盖而不是追加，流水账交给 git |
| 自己拿的主意 | 没问就定的，正是做完时要给用户审的 |

### 归档背景（archive/）

待办做完、决定存下时，压成一份背景，只留以后改它做出来的东西时用得上的：

```markdown
# <名字>

> 完成：YYYY-MM-DD

## 做了什么、为什么做
<一两句>

## 涉及的文件
- <路径——改动前按路径搜归档，靠的就是这一块>

## 前提
- <现在仍然成立的>

## 取舍
- <现在仍然成立的选择，以及当时为什么这么选>
```

完成标准和现状是给执行用的，不进背景。它做出来的东西被改了，背景跟着改；整个被重写或删掉，背景就删。

### requirements.md（1-requirements/）

为什么做、给谁用、长期不做什么。**整份都是核心区**：很少改，每次改都要有 ADR；`context.md` 的「是什么」「不做什么」是它的摘要，跟着改。

```markdown
# <项目> · 需求

> 更新：YYYY-MM-DD
> 改动要有 ADR；`context.md` 的「是什么」「不做什么」是本文件的摘要，跟着改。

## 1. 要解决什么
<给谁用、在什么场景下用、解决什么问题>

## 2. 边界
- 做：<长期范围>
- 不做：<长期不做的，以及为什么>
```

这一阶段做到哪不写在这里，写在 `architecture.md` 的阶段区：它每个阶段都变。

### architecture.md（2-design/）

| 区 | 必备块 | 怎么改 |
|---|---|---|
| **核心区** | 原则与硬约束：技术上不能违反的 | 很少改，每次改都要有 ADR |
| **阶段区** | 描述的是 roadmap 哪个阶段；这一阶段做到哪（砍掉的标明挪到第几阶段）；当前架构（形态、模块、技术栈、目录与接口、数据流）；已知风险 | 开新阶段时整段重写 |

两个区要看得出来：分成两大部分，或者在顶部用分区表标出。

**不放进架构文档：** 待定事项（→ `plans/`）、决策理由（→ `devlog.md`）、历史（→ git 和 roadmap 阶段表）。架构文档一旦变成待办清单，就没人把它当架构读了。

**有真内容时才建。** 先设计后写代码的项目，第一个定案的设计话题就是它的第一份内容：阶段区写计划中的架构。

### testing.md（4-testing/）

怎么验证一次改动没把东西弄坏。**只写仓库推导不出来的**：`package.json` 里已经有 `npm test`，这里写一句「见 `npm test`」，不抄命令。

```markdown
# <项目> · 测试

> 更新：YYYY-MM-DD

## 1. 怎么跑
| 命令 | 测什么 |
|---|---|

## 2. 测不到的
- <只有发布、部署或真人操作之后才能验证的>

## 3. 手工验收
<没法自动化、发布前要人做的步骤>
```

待办的完成标准里那条「项目已有的测试全过」，指的就是这里的命令。**门槛：项目有测试，或者有发布前要人做的验收步骤。**

### release.md（5-release/）

```markdown
# <项目> · 发布

> 更新：YYYY-MM-DD

## 1. 版本号
<写在哪（只写一处）；什么改动升哪一位>

## 2. 发布前检查
- [ ] `testing.md` 的命令全过
- [ ] `CHANGELOG.md` 写好这一版
- [ ] <项目自己的>

## 3. 发布步骤
<一步一步，能照着敲>

## 4. 回滚
<发布出了问题，怎么退回上一个能用的版本>
```

**回滚一块不能写「无」。** 它是唯一只在出事时才有人读的一块，平时谁都发现不了它缺；发布了却退不回去，就写清楚退不回去、出事时怎么办。**门槛：第一次发布。**

### CHANGELOG.md（仓库根目录）

每个版本改了什么，给使用者看。放在仓库根目录，这是它的通行位置，也会跟着发布物一起分发。

```markdown
# 更新记录

> 每个版本改了什么，最新的在最上面。破坏性改动带迁移步骤。

## 未发布

## x.y.z · YYYY-MM-DD

### 破坏性改动
- <改了什么>。迁移：<使用者要做的事>

### 新增

### 改动

### 修复
```

- **只写使用者感觉得到的改动**，内部重构不写
- **破坏性改动在改的那个会话里就写进「未发布」**：迁移步骤此时最清楚，等到发布时再从 diff 里倒推，最容易漏
- 发布时把「未发布」改成版本号和日期，再按 git log 补齐其余的
- **门槛：第一次发布。**

### 图（diagrams/）

图放进它所画的那层决策所属的环节：

| 图 | 放哪 |
|---|---|
| 系统上下文图（决策第 0、1 层：给谁用、和谁打交道） | `1-requirements/diagrams/` |
| 结构、行为、数据、部署的图（决策第 2～5 层） | `2-design/diagrams/` |
| 发布与更新怎么走的图（谁先谁后、本机怎么生效） | `5-release/diagrams/` |
| 代码级的图 | 不进 `docs/`：写代码前画的一次性草图，代码一改就过时 |

**AI 以文字为准。** 图里的结论必须同时写在 `requirements.md`、`architecture.md` 的文字里：图片和白板文件，AI 读起来贵，也读不准。图和文字说得不一样时，以文字为准，并把那张图标成过期。**门槛：真画了图。**

### devlog.md

**只放现在有效的决策。** 每条 ADR 的格式：背景／候选方案／选择／理由／代价／何时重审／落地 commit。落地 commit 让「决策 → 实现」能回溯。

1. 整条失效 → **删除**。取代它的新 ADR 在背景里写一句：取代了什么、原文在哪个 commit
2. 部分失效 → 删掉失效的那部分
3. 编号是永久 ID：删了留空号，**不重排**——commit message 里引用的编号改不了，一重排就全部指错
4. 删之前先核对：取代它的 ADR 有没有装下旧 ADR 里仍然有效的部分，没装下的先并进去
5. 「何时重审」是唯一往前看的一栏：其余各栏都在回答当初为什么这么选，只有它回答什么时候该改

### roadmap.md

阶段表，每个阶段一行。**阶段不是时间段，是「这一批工作解决一个问题」。** 不列条目、不放指针：做了什么在 git 里，为什么在 devlog 里。

```markdown
| 阶段 | 时间 | 解决了什么 |
|---|---|---|
| 1 · <问题> | YYYY-MM-DD ～ MM-DD | <一句话> |
```

### backlog.md

在这个项目里用 groundwork 时，groundwork 本身带来的摩擦。**项目自己的待定事项不在这里**，在 `plans/`。

```markdown
# groundwork backlog · <项目>

> 在这个项目里用 groundwork 时，groundwork 本身带来的摩擦。

## B-01 · <短标题>
**实际发生**（YYYY-MM-DD）：<具体经过>
**要定什么**：<需要改什么>
```

门槛同话题：真的在这里、用 groundwork 时发生过。编号顺序递增、不复用；解决了就删掉那一条，空了就删文件。

## 提交（四个模式共用）

每个模式提交自己写的东西，只提交这些：

1. **动笔前先记下哪些文件已经有未提交的改动**（`git status --short`），这些绝不提交——会把用户进行中的改动卷进来。在报告里列出来
2. **按路径暂存，只暂存这次写的**：`git add <路径>`、`git mv`、`git rm`。绝不用 `git add -A` 或 `git add .`
3. **一次运行一个 commit。** message 照仓库最近提交的语言和风格写（`git log --oneline -10`）；还没有历史就用中文
4. **绝不 push**
5. **`git add` 因为路径被 ignore 而拒绝 → 停下报告**，不用 `-f` 硬加：有人选择了忽略它，这些文档该不该进 git 是他的决定
6. **用户说过不要提交**（这次会话或常驻指令里）→ 只列出改动的文件

## 四个模式共用的约束

- **ADR 一律先问用户**，没有哪个模式能自动写；这条高于别处任何「直接执行」的设置
- `context.md` 可以直接写，不必逐条确认
- 任何一步失败，如实报告卡在哪，不用「已完成」糊过去
- 文件一律写成 UTF-8

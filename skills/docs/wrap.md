# 收尾：会话结束时把变化写回文档

## 1. 预检

- 没有 `docs/context.md` → 停下，让用户先跑 `/groundwork:docs 建档`。不要绕过骨架硬写
- 动笔前记下哪些文件已经有未提交的改动（见 SKILL.md「提交」）

## 2. 回顾这次会话

从头读一遍这次会话，判断：

- 推进了哪份待办？
- 有没有**开了工、没做完、又没有待办文件**的工作？
- 顶层模块有没有增减？
- 有没有撞到过得了三道检查的**结构性的坑**？
- 有没有做出不显然的技术决定（有候选方案、有理由的那种）？
- 有没有冒出该做、但现在不做的事？讨论里有没有被点出来的跑题？
- 讨论过哪个话题、哪份草案？有没有话题定了、放弃了，或者被顺手做完了？草案里有没有哪部分定了？
- 改了哪些文件？（第 7 步按这些文件核对归档背景）
- groundwork 本身有没有碍事？

参数里 `收尾`／`wrap` 后面的内容，是用户对重点的提示，但以会话实际为准。

## 3. 直接改 `context.md`（不用逐条确认）

- **顶层模块表**：只在模块真的增减时动。**每个模块一行职责，以目录为键**——hook 不列目录，键就是位置；模块内部的布局归 `design.md`
- **结构性的坑**：按三道检查和「永久、反复撞」过滤
- **日期行——绝不跳过。** 改它才算标记已核对、重置过期基线。跳过的话，之后每次会话都带着「context.md 可能过期」，几轮下来 AI 学会无视它，**整个过期防护就失效了**

## 4. 待办

- **推进了的**：覆盖「现状」（做完了什么、下一步、卡在哪）；没问用户就定的选择，追加到「自己拿的主意」；能验证的完成标准打勾
- **开了工、没做完、又没有待办文件的**：按 SKILL.md 的待办模板新建一份，序号排在最后（要插队就问）。目标和完成标准从这次会话里取，「现状」写清做到哪了。这是待办的第二个来路——会不会跨会话，常常做到一半才知道

## 5. 话题与 backlog

- **新话题**：新建 `plans/<层级>-<名字>.md`，层级按它影响到的最早一层算。讨论中被点出来的跑题，也在这里落成话题
- **讨论过的话题**：讨论记录追加一行带日期的
- **定案成设计** → **先问**：定没定是判断，和「做完没有」一样，写进 `design.md` 的结论，之后每个会话都会当成定论。确认后写进对应的区，`git rm` 话题。核心区的结论要先过第 9 步的 ADR 询问
- **放弃** → 理由不显然的，在第 9 步问要不要记 ADR；然后 `git rm`
- **顺手做完** → `git rm`；结果是长期成立的事实，写到它该在的地方
- **只定了一部分** → 定了的写进 `design.md`、从「要解决什么」里划掉，文件留着
- **阶段草案**：这次起草或改了草案 → 按 SKILL.md 的阶段草案模板写进去，讨论记录追加一行。草案里定下的部分 → 和「定案成设计」一样**先问**，确认后写进 `design.md`、从草案里划掉；要干的活写成待办（第 4 步）。拖得整份草案关不掉的、挪到后面阶段的 → 拆成单独的话题。全部定完 → `git rm`
- **groundwork 本身碍事了** → `backlog.md` 加一条（第一条时连头部一起建）
- **门槛：真的发生过。** 话题和 backlog 都一样，没有就什么都不写，也不问

## 6. 做完的待办（先问）

所有完成标准都打了勾，或者用户说做完了，就是候选。对每一份，**给出存或删的建议和理由，由用户拍板**：

- 判据只有一条：**以后改它做出来的东西时，AI 需要这份背景吗？** 前提或取舍里有代码、`design.md`、ADR 都看不出来的东西 → 建议存；纯机械的工作（翻译、迁移、改名），或者理由已经全写在某条 ADR 里（先核对真的写了）→ 建议删
- **存**：先把「自己拿的主意」里被用户否掉的删掉；`git mv docs/tasks/<序号>-<名字>.md docs/archive/<完成日期>-<名字>.md`，再按 SKILL.md 的归档背景模板改写成四块
- **删**：`git rm`
- 删掉或移走之后，后面的待办不必改序号——序号只表达先后，空号无妨

## 7. 核对归档背景

用第 2 步列出的「改了哪些文件」在 `docs/archive/` 里搜一遍：

- 命中，且这次的改动让背景里某条不再成立 → 直接改掉那一条（`change-scope` 应该已经在改代码时改过，这里补漏）
- 整份背景都不成立了（它做出来的东西被重写或删掉）→ **问用户删不删**

## 8. design.md 与阶段

- 这次会话改了目标、原则或边界 → 那是核心区的改动，要过第 9 步的 ADR 询问，`context.md` 的「是什么」「不做什么」跟着改。没有 ADR 绝不改核心区
- **开新阶段是判断，问用户。** 用户开了新阶段：roadmap 阶段表加一行；建这个阶段的草案 `plans/1-<阶段>草案.md`——这次会话里已经谈出了草案就写进去，还没有就按模板建一份「还没起草」的。`design.md` 的阶段区等草案里的内容定下来，再按定下的重写。收尾从不自己开阶段

## 9. ADR（绝不直接写）

第 2 步、第 5 步的定案或放弃、第 8 步里出现了不显然的决定 → **停下问**：「要不要为这个记一条 ADR？<候选标题 ＋ 一句背景>」

- 用户说要 → 按 SKILL.md 的格式追加到 `docs/devlog.md`（没有就建），带上**落地 commit**
- 新 ADR 取代了旧的 → 按 devlog 规则同步删除或删改旧的那条，并在新 ADR 的背景里写明取代了什么、原文在哪个 commit
- 用户说不要，或者决定太小 → 不写

**ADR 的门槛比这里任何东西都高。** 别让第 3 步「直接写」的习惯蔓延到 devlog：`git log` 记的是改了什么，ADR 记的是「考虑过 A/B/C，选 B，因为 X，代价 Y」——git 替代不了它，但写太多会把信号淹掉。

## 10. 提交和报告

提交这次写的全部（见 SKILL.md「提交」），然后报告：

- `context.md` 改了哪几节
- 待办：推进了哪些、新建了哪些、做完的存了还是删了
- 话题：新记了哪些、各自的结局
- 归档背景改了哪份、改了什么
- 有没有问 ADR、答复是什么
- commit 是哪个；哪些文件因为已经有进行中的改动而没提交

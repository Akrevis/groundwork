# task（待办）：把定下来的事写成待办

治两种毛病：**AI 从没人说过的前提往下推**，和 **AI 没验证就说做完了**。产出是一份或几份待办，之后的会话拿着就能开工，不用再问文件里已经答过的事。

## 什么时候用

| 情况 | 用吗 |
|---|---|
| `plans/` 里的话题、阶段草案里的某部分讨论到定了，留给之后做 | 用——最常见 |
| 一个会话讨论出好几件要之后做的事 | 用——一次开多份 |
| 新的、不小的工作，想直接开工、不先讨论 | 用 |
| 当场就能做完的 | 不建文件；但第 2～4 步的复述、前提、完成标准照样做，在对话里确认 |
| 改名、调格式、修错字、纯查阅、一次性脚本 | 不用 |
| 拿不准 | 问自己：这事要是走偏了，会有人需要回头查当时说定的是什么吗？会 → 用 |

## 1. 预检

- 没有 `docs/context.md` → 停下，让用户先跑 `/groundwork:docs init`
- **来源**：参数里 `task` 后面的内容，指明 `plans/` 里的话题、草案，或描述新工作；没有就问。来源是话题或草案 → 先读完整份，前提多半在它的讨论记录里

## 2. 用自己的话复述目标和边界

**要什么**、**边界在哪**（明确不做的）。几件事一起开，就逐件复述。

**不要复读用户的原话**——复读证明不了什么，这一步的全部意义，是在开工前把误解暴露出来。

## 3. 列出你推断的前提（不能省）

逐条列出你要依赖、但用户从没说过的东西，**标明是推断，不是要求**：

- 用户没说存哪 →「我假设存在 `data/`，你没说」
- 用户没说要不要兼容旧格式 →「我假设不兼容，只支持新格式」

**为什么必须明说**：从没人说过的前提往下推，做出来的东西看着完整，方向却是歪的，而且**很难看出来**——假设埋在实现里，要到运行时才冒出来。

**列不出就说列不出**，不要凑两条无关痛痒的。

## 4. 说清什么算做完

必须**可验证**，不能是形容词：

| ✗ 不是标准 | ✓ 是标准 |
|---|---|
| 代码质量好 | `node test.js` 13 项全过 |
| 体验流畅 | 首屏 < 1 秒（DevTools 实测） |
| 重构完成 | 原有测试全过 ＋ 新增 3 个边界用例 |

**标准在动手前定，不是做完再补。** 做完再写的，只是对做出来的东西的描述，等于什么都没定。

## 5. 查归档背景

用这件事要改的文件路径在 `docs/archive/` 里搜一遍。命中的是当初做出这些东西的任务背景：读它的前提和取舍，**仍然成立的带进这份待办的前提里**。没有 `docs/archive/` 就跳过。

## 6. 定顺序

看 `docs/tasks/` 里已有的待办，定这份排在哪：

- 排在最后 → 取下一个序号
- 要插队 → 定好位置，后面的待办顺延改名（`git mv`），在报告里说明
- 几件一起开 → 按开工顺序连续编号

## 7. 停下等确认

把第 2～6 步一起交给用户，**等他确认或改正之后再写任何东西**。

「不确定就停」落在这里：**该停的时刻是现在**，不是做到一半发现不对的时候。

## 8. 写入、撤掉话题、提交

- 按 SKILL.md 的待办模板写 `docs/tasks/<序号>-<名字>.md`；「现状」写「刚开立」，「自己拿的主意」写「无」
- 来源是话题或草案：转成待办的部分从里面拿掉——空了就 `git rm`，没空就只删那部分。草案里定下的框架写进 `design.md` 是收尾的事，这里不动
- 一起提交（见 SKILL.md「提交」）

不用另外登记：hook 自己读 `docs/tasks/`，待办一存在，下次会话的注入里就有它。

## 9. 报告

- 第 2～6 步确认后的结论
- 写了哪些待办、各自的序号，commit 是哪个
- **怎么执行**：在任何新会话里说「做 `docs/tasks/<文件>`」即可
